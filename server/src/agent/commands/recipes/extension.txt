Call `get_documentation` with `{"section":"extensions"}` before building an
extension. It is the canonical, complete API reference. The rules below cover
the paths most likely to fail.

## Safety and lifecycle

- Only install when the user explicitly asks.
- Never call `activate` or `deactivate`; Vektor owns the module lifecycle.
- Do not keep `ctx` in global scope. Register behavior inside `activate`.
- `activate` returns `void`; a cleanup function returned from it is ignored.
  Put module cleanup in `deactivate`. A *view renderer* may return a cleanup
  function, which Vektor runs when that rendered view unmounts.
- Action and suggestion IDs are automatically prefixed with the extension ID.
  They are also cleaned up on unload, though explicit unregistering is valid.
- Extension IDs use lowercase letters, digits, and hyphens.

## Manifest

An extension needs `manifest.json` and at least one entry file.

Actions or suggestions only:

```json
{
  "id": "my-ext",
  "name": "My Extension",
  "version": "1.0.0",
  "description": "...",
  "entries": { "frontend": "dist/main.js" }
}
```

Standalone or document-side view:

```json
{
  "id": "my-ext",
  "name": "My Extension",
  "version": "1.0.0",
  "entries": { "view": "dist/view.js" },
  "routes": [
    {
      "path": "my-ext",
      "title": "My Extension",
      "menuItem": { "title": "My Extension" },
      "placements": ["standalone", "inline", "document", "database"]
    }
  ]
}
```

- `entries.frontend` and `entries.view` are independently optional. A view-only
  extension does not need a frontend entry.
- Routes require `entries.view`, and a view entry requires at least one route.
- `placements` defaults to `["standalone"]`. Add `"inline"` to make the view
  available through the Add Content menu, or `"document"` to render beside
  standard documents on desktop. Add `"database"` to expose it as a database
  view tab; `ctx.documentId` is the current database while that view is mounted.
- Every entry path declared in the manifest must exist in the ZIP.

## Frontend entry

```js
export function activate(ctx) {
  ctx.actions.register('hello', {
    title: 'Say hello',
    run: async () => { alert('hello'); },
  });
}

export function deactivate(ctx) {
  ctx.actions.unregister('hello');
}
```

Frontend entries are loaded for installed extensions in the active space.
Register actions and suggestions there; render route UI through a view entry.

## View entry

The registered path must exactly match `routes[n].path`:

```js
export function activate(ctx) {
  ctx.views.register('my-ext', (container) => {
    container.innerHTML = '<h1>My Extension</h1>';
    return () => { container.innerHTML = ''; };
  });
}

export function deactivate(ctx) {
  ctx.views.unregister('my-ext');
}
```

Views render inside a shadow DOM and must provide their own styling.

## API client

Use `ctx.api` and `ctx.spaceId`:

```js
const { documents, nextCursor } =
  await ctx.api.documents.get(ctx.spaceId, { limit: 100 });
const doc = await ctx.api.document.get(ctx.spaceId, documentId);
const created = await ctx.api.documents.post(ctx.spaceId, {
  title: 'My Doc',
  content: '<p>Hello</p>',
  type: 'document',
});
await ctx.api.document.put(ctx.spaceId, documentId, '<p>Updated</p>');
await ctx.api.document.patch(ctx.spaceId, documentId, {
  properties: { status: 'published' },
});
const { results } = await ctx.api.search.get(ctx.spaceId, { q: 'hello' });
```

## Collaboration and presence

`ctx.collaboration` is available only while a canvas or editor document is
active. It exposes `{ydoc, clientId}` for persistent, document-bound shared
state. Always guard it:

```js
export function activate(ctx) {
  if (!ctx.collaboration) return;
  const state = ctx.collaboration.ydoc.getMap('my-ext.state');
  state.set('score', 0);
}
```

For ephemeral multiplayer state on standalone routes, use `ctx.presence` instead of
writing peer records into a YMap:

```js
export function activate(ctx) {
  ctx.views.register('my-ext', async (container) => {
    const room = await ctx.presence.connect('main', {
      state: { status: 'ready' },
    });
    const unsubscribe = room.subscribe((event) => console.log(event));
    return () => {
      unsubscribe();
      room.leave();
      container.innerHTML = '';
    };
  });
}
```

Call `room.update(nextState)` to publish local presence changes. Presence rooms
are ephemeral and must not be used as document storage.

## Jobs

Jobs run in Vektor's sandboxed Boa JavaScript VM, not Node or worker_threads.
Add a job definition to the manifest:

```json
{
  "jobs": [
    {
      "id": "word-count",
      "name": "Word Count",
      "entry": "dist/word-count.js",
      "inputs": { "documentId": { "type": "string", "required": true } },
      "outputs": { "words": { "type": "text" } }
    }
  ]
}
```

Job entry:

```js
const { documentId } = input;
if (!documentId) throw new Error('Missing documentId');

const content = await readDocument(documentId);
log(`Read ${content.length} bytes`);
await output({
  words: { type: 'text', value: String(content.trim().split(/\s+/).length) },
});
```

- Job bundles contain no `import`, `export`, `require`, or `node:*` usage.
- Results go through `output()`; throwing fails the run.
- Available capabilities include document operations, `fetch`, `apiFetch`,
  `uploadArtifact`, secrets, archives, spreadsheets, scratch storage, cache,
  timers, and `agentPrompt`. Use the canonical extension documentation for
  exact signatures.

## Package and install

The agent sandbox has no package manager or general build tool. Write already
bundled browser/job JavaScript into `dist`, or provide a self-contained source
that needs no build step.

Zip from inside the extension directory so `manifest.json` is at the ZIP root:

```bash
cd my-ext
zip ../my-ext.zip .
zipinfo ../my-ext.zip
extension install ../my-ext.zip
```

Run `zipinfo` before installation. The listing must show `manifest.json` and
every declared entry at the expected root-relative path.
